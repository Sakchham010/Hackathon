# cursor-model-router

Passive telemetry, task classification, and outcome collection for Cursor
Agent usage. `cursor-model-router` installs a set of fail-open, user-level
Cursor hooks that observe normal Cursor Agent conversations as they happen,
store what happened in MongoDB, classify each finished task, and (optionally)
run trusted, repository-defined build/test checks afterward.

It does **not** run the same task repeatedly across different models, launch
Cursor agents itself, or produce a "best model" recommendation. It only
collects and organizes observational data so that kind of analysis can be
done responsibly later, with the sample-size and selection-bias caveats that
observational data requires.

## How it fits together

```
Cursor Agent conversation
        │  (sessionStart, beforeSubmitPrompt, preToolUse, postToolUse,
        │   postToolUseFailure, afterFileEdit, stop, sessionEnd)
        ▼
  router hook   ──(MongoDB reachable)──▶  tasks / task_generations / task_events
        │
        └──(MongoDB unreachable)──▶  local spool (~/.cursor-model-router/spool)
                                              │
                                    router spool drain
                                              ▼
                                tasks / task_generations / task_events

router classify pending   ──▶  task_classifications  (rules, optionally + LLM)
router outcome extract-signals ──▶ outcome_signals    (weak, non-authoritative)
router verification run-pending ──▶ verification_runs (trusted repo checks)
router outcome record           ──▶ verification_runs (user/CI-submitted results)
```

Telemetry writes are keyed so retries and duplicate hook deliveries are
no-ops. Verification results are append-only records, and every free-text
field (prompts, commands, tool/build output) is redacted and truncated before
it is persisted.

### Conversation tasks vs. generation tasks

A **conversation task** (`tasks`) is the whole Cursor Agent session: one
`conversation_id`, from `sessionStart` to `sessionEnd`. It owns
session-level data — overall status, repository/workspace roots, and
router-executed/user-submitted verification runs.

A **generation task** (`task_generations`) is one prompt/turn within that
conversation: one `(task_id, generation_id)` pair, from its
`beforeSubmitPrompt` to its own `stop`. It owns exactly one prompt
(`prompt_preview`) and the model/model ID/repository root that were active
when that prompt was submitted (captured once, never overwritten by a later
turn in the same conversation). `task_events` are still recorded under the
parent conversation's `task_id`, but each event also carries the
`generation_id` of the turn it belongs to (hooks that arrive without one are
grouped under an explicit `unscoped` bucket rather than being silently
merged into whichever generation happens to be open).

Classification and generation-scoped outcome signals key off the
**generation's own task id**, not the conversation's, so:

- A prompt's category/intent reflects only that prompt's own text — never a
  later turn's activity, and never a tool failure from carrying it out.
- Once a generation is classified, no amount of later activity in the same
  or a later generation can change it.

## Installation

```powershell
py -3.10 -m venv .venv
.\.venv\Scripts\pip install -e ".[dev]"
```

1. Start MongoDB (a local instance is enough to get going):

   ```powershell
   docker compose up -d
   ```

   This runs MongoDB on `localhost:27117` (mapped from the container's
   `27017`, so it never collides with a MongoDB you already run locally). Set
   `CURSOR_MODEL_ROUTER_MONGO_URI` to point at MongoDB Atlas or another shared
   instance instead if you want multiple machines/users writing to the same
   database.

2. Initialize collections/indexes (safe to re-run any time):

   ```powershell
   router db initialize
   ```

3. Install the Cursor hooks into `~/.cursor/hooks.json`:

   ```powershell
   router hooks install
   ```

   This only ever adds/updates entries whose `command` was generated by this
   installer; every other hook you already have configured is left alone. A
   timestamped backup of `hooks.json` is written before any change.

4. Start using Cursor normally. Nothing changes in the Cursor UI. Telemetry
   accumulates in MongoDB as you work.

To remove the hooks (and leave everything else in `hooks.json` untouched):

```powershell
router hooks uninstall
```

## Configuration

Configuration lives at `~/.cursor-model-router/config.yaml` (override the
path with `CURSOR_MODEL_ROUTER_CONFIG`). Nothing in the file is required; all
fields have safe defaults. Example:

```yaml
mongo_uri: mongodb://localhost:27117
database_name: cursor_model_router

retention_days: 180

redaction:
  max_prompt_chars: 10000
  max_tool_output_chars: 2000
  max_command_output_chars: 4000
  persist_file_contents: false
  persist_full_tool_output: false

repositories:
  # If `allow` is empty, every repository not explicitly denied is observed.
  allow: []
  deny:
    - "c:/work/some-sensitive-repo/*"
  ignored_path_globs:
    - "**/.git/**"
    - "**/node_modules/**"
    - "**/*.env"

classification:
  low_confidence_threshold: 0.5
  llm_enabled: false          # opt-in only; rules classification always runs

verification:
  repo_config_file_name: ".cursor-model-router.yaml"
  default_command_timeout_seconds: 600
  trusted_repositories:
    - path_glob: "c:/work/appian-monorepo/*"
      max_command_timeout_seconds: 900
```

`CURSOR_MODEL_ROUTER_MONGO_URI` and `CURSOR_MODEL_ROUTER_DATABASE` environment
variables override the corresponding config-file values, which is convenient
for tests and CI.

### Privacy and retention

- Prompts, shell commands, tool error messages, and check output are
  redacted (common credential/secret patterns are masked) and truncated
  before they are ever written to MongoDB.
- File *contents* and full tool output are never persisted
  (`redaction.persist_file_contents` / `persist_full_tool_output` default to
  `false`; there is currently no supported way to turn these on without
  changing the code, by design).
- `repositories.deny` / `repositories.allow` control which repositories are
  observed at all; denied or non-allow-listed repositories are never written,
  not even redacted.
- `retention_days` documents the intended retention policy; enforcing it
  (e.g. a scheduled deletion job keyed on `started_at`) is left as an
  operational task for whoever runs the database.

## Repository-defined verification checks

A repository can ship its own `.cursor-model-router.yaml` describing checks
to run after a Cursor conversation ends:

```yaml
version: 1
checks:
  - name: build
    check_type: build
    command: "dotnet build"
    working_directory: "."
    timeout_seconds: 600
  - name: unit_tests
    check_type: test
    command: "dotnet test"
    timeout_seconds: 900
```

**A repository cannot grant itself permission to run these commands.** Only a
`path_glob` entry under `verification.trusted_repositories` in your own
central config does that. Without a matching trust entry, the router records
a single `skipped` verification run and never executes anything from that
repository's file.

Once trusted, run the check worker (e.g. from a scheduled task):

```powershell
router verification run-pending
```

Each check's command, exit code, duration, timestamps, commit, working-tree
dirty flag, and a redacted/truncated output excerpt are recorded in
`verification_runs` with `source: router_verification`.

## Submitting your own build/test results

If you'd rather run checks yourself (existing CI, a different local hook, a
person eyeballing the result), submit them directly:

```powershell
router outcome record `
  --task-id <task-uuid> `
  --verification-method manual `
  --check-type behavior `
  --status passed `
  --exit-code 0 `
  --duration-ms 4200 `
  --commit <sha>
```

`verification-method` must be `automated`, `manual`, or `not_verifiable`;
`check-type` must be `test`, `build`, `lint`, `behavior`, `research`, or
`other`. `status` records the task-level result and may be `passed`,
`partially_passed`, `failed`, `timed_out`, `error`, `inconclusive`, or
`skipped`. Submissions are recorded with `source: user_submitted`. Repeated
submissions are retained as separate evidence records.

## Classification

Every finished **generation** (one prompt/turn, not a whole conversation) is
classified by a deterministic rules classifier that derives category,
subcategory, and intent from that generation's own prompt text only —
never from what happened while carrying it out. Complexity, cross-file
scope, and primary language are measured from that same generation's own
edits (`after_file_edit` events only; read-only tool accesses are not
scope). Tool failures, stack traces seen in tool output, and build/test
activity are recorded as **outcome evidence** in the `evidence` field, but
never change the category/intent a prompt is classified as — a failure
encountered while adding a feature is still a `feature` request, not a
`debugging` one.

Each `task_classifications` document carries two ids: `generation_task_id`
(the generation's own `task_generations._id`, unique together with `source`
— this is what classification is idempotent per) and `task_id` (the parent
conversation's `tasks._id`, carried alongside purely so a conversation's
classifications can be looked up without a join):

```powershell
router classify pending
```

An optional LLM classification path exists (`classification.llm_enabled`) and
only runs when the rules classifier's confidence is below
`classification.low_confidence_threshold`. It is disabled by default, stores
its own `source: llm` record alongside (never instead of) the rules result,
receives the same prompt/activity separation as the rules classifier, and
requires you to supply your own HTTP classification endpoint — this project
does not bundle a vendor SDK or a hosted classification service.

## Outcome signals

`router outcome extract-signals` derives weak, non-authoritative signals,
split the same way classification is:

- **Conversation-level** (keyed to the conversation's own task id):
  `agent_status` (overall completion status) and `follow_up_generation`
  (whether the conversation had more than one prompt/turn).
- **Generation-level** (keyed to each generation's own task id):
  `tool_failure`, `shell_exit`, and `build_test_activity`, each scoped to
  that generation's own events only.

None of these collapse into a `success = true/false` label — that judgment
call is deliberately left to whoever analyzes the data, with router-executed
and user-submitted verification results kept as separate, clearly-sourced
evidence.

## Exporting for analysis

```powershell
router export --output tasks.jsonl --format jsonl
router export --output tasks.parquet --format parquet   # requires: pip install -e ".[export]"
```

Each row is one conversation, with its `task`, conversation-level
`outcome_signals`, and `verification_runs`, plus a nested `generations` list
where each entry carries its own prompt, `classifications`, and
generation-level `outcome_signals`. The export intentionally does not
compute or print a "best model" ranking.

## Local review console

The router can expose a localhost-only FastAPI API and React review console.
Cursor remains the place where work happens; the console is for inspecting
collected evidence and appending human or CI verification without changing
the Cursor workflow.

Install the backend extra and frontend dependencies:

```powershell
.\.venv\Scripts\pip install -e ".[dev,web]"
cd web
npm install
```

Start MongoDB and the API in one terminal:

```powershell
router db initialize
router serve
```

For frontend development, start Vite in another terminal:

```powershell
cd web
npm run dev
```

Open `http://127.0.0.1:5173`. The inbox shows completed conversations that
have no `user_submitted` verification by default. A conversation page joins
its generations, classifications, bounded activity summaries, outcome
signals and router checks. Review actions append
`user_submitted` verification runs; they never overwrite observed or
router-executed evidence.

`router serve` binds to `127.0.0.1` by default and accepts only the local
Vite/preview origins. The API can serve `web/dist` after `npm run build`.
The v1 UI does not provide authentication, a non-loopback bind, live chat
streaming, model recommendations, or arbitrary command execution. Only
repository checks already trusted in central router configuration can be run
from the conversation page.

## Observational-data limitations

This dataset reflects whatever a person actually chose to do in Cursor. It is
useful for spotting associations between a task class and a model's observed
outcomes, but:

- Model choice is not randomized, so differences may reflect what kinds of
  tasks people route to which models rather than model capability.
- Sample sizes per (task category × model) cell can be small; any downstream
  analysis should report sample size and uncertainty, not a single "winner."
- Treat every conclusion as a hypothesis to validate, not a routing decision
  to automate, until far more data (and ideally some deliberate variation) is
  available.

## What's intentionally missing

- **No exact token usage or billed cost for normal IDE sessions.** Cursor
  hooks do not expose this without a Cursor Team Admin API key; the schema
  has no per-run cost field, and no code in this project estimates or
  fabricates one.
- **No automatic model recommendation or routing.** This is a data collection
  and classification MVP; using the data to actually choose a model is a
  deliberately separate, later decision.
